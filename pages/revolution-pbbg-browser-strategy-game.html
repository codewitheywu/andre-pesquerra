Revolution — Persistent Browser-Based Multiplayer Strategy Game

A persistent browser-based multiplayer game (PBBG) built on native PHP, MySQL, and vanilla JavaScript. Tribal strategy at its core — resource economies, research trees, syndicates, live chat, and a roguelite combat module, all running inside a single AJAX-driven page.

Overview

🌱 The Beginning — Foundation & Planning
Revolution started as a client project with a deceptively simple brief: a browser game people could keep coming back to. No engine, no framework — just native PHP with PDO, MySQL, and vanilla JavaScript. Every system had to be designed from the database up.

The first decision shaped everything after it: a single-entry architecture. One index.php, every interaction routed through AJAX and gated by $_POST['action']. No page reloads, no fragmented state — the whole game lives on one screen and rewrites itself as the player moves through it.

🏗️ Building the World
The Monolith became the hub — chat, stylist, shop, syndicates, trainer, hunting board, and proving grounds all under one roof. From there the game grew outward:

• Resource management — Lumber, Mining, and Farm systems, each with its own research skill tree and workforce assignment, so players allocate limited labor across competing economies.
• Bullet storm roguelite — a self-contained action module (crimes_against_humanity.php) that breaks the strategy loop with something fast and twitchy.
• Syndicates — the social layer, where players group up and compete for territory and standing.
• Achievements — long-tail progression that gives returning players something to chase.

🎯 The Approach
I handled the entire stack solo: schema design, backend logic, frontend behavior, and UI/UX. Working against a live MySQL database through DBeaver, deploying PHP over FTP with FileZilla, and iterating directly against real player data rather than a sandbox.

Discipline mattered more than cleverness. All JavaScript declared as globals in index.php instead of scattered inline scripts. Data handed to the frontend through base64-encoded data-* attributes so nothing broke on quoting or encoding. Consistent asset path prefixes so the live deployment and local WAMP build behaved identically.

Challenges

🛠️ Technical Challenges
Building a persistent multiplayer world without a framework means you are the framework. Every problem below had to be solved from scratch:

• State without page reloads — with everything routed through a single entry point, action routing and response handling had to be airtight. A malformed AJAX payload could not be allowed to leave the player stuck in a half-rendered state.
• Passing complex data to JavaScript — inline JSON kept breaking on quotes and special characters inside player-generated content. Base64-encoding into data-* attributes ended that class of bug permanently.
• Script collisions — dozens of interactive modules loading into one page meant JS conflicts everywhere. Declaring everything as controlled globals in index.php made the load order predictable instead of accidental.
• MariaDB vs MySQL drift — DEFAULT current_timestamp() on bigint columns silently failed on the live MariaDB server while working fine locally. It resurfaced repeatedly across migrations until I standardized the column definitions across both environments.
• Case-sensitive deployments — the project directory is destroym_gamePBBG on the live Linux server and destroym_gamepbbg on my Windows machine. Linux does not forgive that. Every path reference had to be verified before deploy, not after.
• Balancing economies — research trees and workforce assignment only feel meaningful if the tradeoffs are real. Tuning those numbers is an ongoing design problem, not a code problem.

Outcomes

🏁 Outcomes
Revolution runs live and persistent, with players moving through the Monolith, building economies, joining syndicates, and grinding achievements across sessions.

What I took away from it:

• Proof that a full multiplayer game loop can be built and maintained on native PHP and vanilla JS — no framework, no build step, no dependency graph to babysit.
• A single-entry AJAX architecture I now reuse across client projects, refined by the failure modes this game exposed.
• Real experience deploying to and debugging against a live production database instead of a comfortable local copy.
• Hard-won environment discipline: casing, timestamp defaults, and path handling are not details on Linux, they are the difference between a working deploy and a white screen.

Most of all, it taught me how to own an entire stack alone — design the schema, write the backend, build the frontend, ship it, then keep it alive while people are playing on it.
