Revolution — Persistent Browser-Based Multiplayer Strategy Game

A persistent browser-based multiplayer game (PBBG) built on native PHP, MySQL, and vanilla JavaScript. Tribal strategy at its core — resource economies, research trees, syndicates, live chat, and a roguelite combat module, all running inside a single AJAX-driven page.

Overview

🌱 Foundation
Revolution started as a client brief: a browser game people would keep coming back to — no engine, no framework, just native PHP with PDO, MySQL, and vanilla JavaScript. The core decision was a single-entry architecture: one index.php, every interaction routed through AJAX and gated by $_POST['action'], so the whole game lives on one screen and rewrites itself as the player moves through it.

🏗️ Building the World
The Monolith is the hub — chat, stylist, shop, syndicates, trainer, hunting board, proving grounds. From there: Lumber/Mining/Farm resource systems each with their own research tree and workforce assignment, a self-contained bullet-storm roguelite module, syndicates for the social/territory layer, and long-tail achievements.

🎯 Approach
I owned the entire stack solo — schema, backend, frontend, UI/UX — working against a live MySQL database via DBeaver and deploying over FTP, iterating directly against real player data. Discipline over cleverness: all JavaScript declared as globals in index.php, data passed to the frontend via base64-encoded data-* attributes to dodge quoting bugs, and consistent asset paths so local WAMP and live deployment behaved identically.

Challenges

Building a persistent multiplayer world without a framework means you are the framework. Routing everything through one entry point meant action routing had to be airtight — a malformed AJAX payload couldn't leave a player stuck mid-render. Inline JSON kept breaking on quotes inside player content until I moved to base64-encoded data-* attributes. Dozens of interactive modules loading into one page caused JS collisions, solved by declaring everything as controlled globals. MariaDB's DEFAULT current_timestamp() on bigint columns silently failed live while working locally — a drift I had to standardize across environments. And the live server's case-sensitive Linux filesystem meant every path had to be verified before deploy, not after.

Outcomes

Revolution runs live and persistent — players build economies, join syndicates, and grind achievements across sessions. It proved a full multiplayer game loop is buildable on native PHP and vanilla JS with no framework or build step, gave me a single-entry AJAX architecture I now reuse on client projects, and taught me real deployment discipline: casing, timestamp defaults, and path handling aren't details on Linux, they're the difference between a working deploy and a white screen. Most of all, it taught me to own an entire stack alone — schema to backend to frontend to keeping it alive while people play.
