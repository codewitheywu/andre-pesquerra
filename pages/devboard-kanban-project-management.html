DevBoard — Drag-and-Drop Kanban Project Management Tool

A self-built kanban board for tracking development work — boards, columns, and cards with full drag-and-drop reordering, task assignment, and live status updates. Built on native PHP, MySQL, and vanilla JavaScript, and used to run a 3-person development team.

Overview

🌱 Why I Built It
DevBoard started as a personal project born out of a practical problem: I was coordinating work across a small dev team and every existing tool was either bloated, paywalled at the exact feature I needed, or built around a workflow that was not ours.

So I built the board I actually wanted. Native PHP with PDO on the backend, MySQL for persistence, vanilla JavaScript on the frontend — no framework, no build step, no dependency tree to maintain.

👥 Leading the Team
The project stopped being purely personal once three other developers came onto it. I led the team: setting the direction, defining the data model, dividing the work, reviewing what came back, and making the final calls on architecture.

That changed how I had to build. Code that only I would ever touch can be as clever as I like. Code that three other people are writing against needs consistent naming, predictable structure, and conventions everyone follows. Deciding those conventions up front — and then actually holding to them in review — turned out to be the most important thing I did on this project.

It also meant DevBoard was dogfooding itself: we tracked our own work on the board while building it. Every friction point in the interface got felt firsthand within a day.

🎯 The Build
The core is a familiar kanban model — boards contain columns, columns contain cards — implemented with a relational schema where card position and column membership are first-class persisted data, not just visual state.

Drag-and-drop was the centerpiece. A card should move the instant you release it, with the board reflecting the new order immediately and the database catching up behind it. Every drop fires an asynchronous request that writes the new column and position, while the interface has already moved on.

On top of that sits task assignment, so each card has an owner and everyone can see who is holding what at a glance.

Challenges

🛠️ Technical Challenges
Drag-and-drop looks trivial from the outside. It is not.

• Persisting order — the hardest part of any kanban board is not moving the card, it is remembering where it went. Dropping a card between two others means every card below it shifts. Naive approaches rewrite the entire column on every move, which does not scale and floods the database with writes. Getting an ordering scheme that stays stable across repeated reordering took several attempts.
• Optimistic UI vs. reality — the card has to move instantly on drop, before the server confirms anything. That means the interface can be showing a state the database has not accepted yet. Handling the failure case cleanly — reverting the card without confusing the user — required designing for it deliberately rather than assuming requests succeed.
• Concurrent edits — with multiple people on the same board, two users can move cards in the same column at nearly the same moment. Reconciling that without cards disappearing or duplicating meant thinking carefully about how position updates are written and how a stale client refreshes.
• Building drag-and-drop in vanilla JS — no drag library meant handling pointer events, drop zone detection, placeholder rendering, and edge cases like dragging outside the board or releasing over an invalid target, all by hand. Making it feel smooth rather than merely functional was a long tail of small fixes.
• Leading rather than just building — the real challenge was resisting the urge to write everything myself. Handing work to three developers, letting their approach differ from mine where it did not matter, and pushing back where it did, was a different skill from coding. Untangling merge conflicts and inconsistent conventions early taught me to define the structure before distributing the work, not after.

Outcomes

🏁 Outcomes
DevBoard works and was genuinely used — by me and by the three developers I led, to manage the very project it was built for.

What it produced:

• A complete, working kanban tool built entirely from scratch on native PHP, MySQL, and vanilla JavaScript — proof that the polished interactions people associate with heavy frontend frameworks are achievable without one.
• A drag-and-drop implementation I understand at every level, because I wrote every part of it. That understanding transfers directly to every interactive interface I have built since.
• Real technical leadership experience: owning the architecture, dividing work across three developers, reviewing their code, and being accountable for the result.
• A much better instinct for optimistic UI — building interfaces that respond immediately and reconcile with the server afterward, rather than making users wait on a round trip.

The most valuable outcome was not the tool. It was learning that on a team, the architecture decisions you make in the first week determine how much time everyone wastes in the following months.
