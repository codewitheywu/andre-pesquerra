DevBoard — Drag-and-Drop Kanban Project Management Tool

A self-built kanban board for tracking development work — boards, columns, and cards with full drag-and-drop reordering, task assignment, and live status updates. Built on native PHP, MySQL, and vanilla JavaScript, and used to run a 3-person development team.

Overview

🌱 Why I Built It
DevBoard came from a practical problem: coordinating a small dev team when every existing tool was bloated, paywalled at the one feature I needed, or built around someone else's workflow. So I built the board I wanted — native PHP with PDO, MySQL, and vanilla JavaScript, no framework or build step.

👥 Leading the Team
Once three other developers joined, I led the project: setting direction, defining the data model, dividing work, reviewing code, and making the final architecture calls. Code three other people write against needs consistent naming and conventions everyone actually follows — deciding those up front, then holding to them in review, was the most important thing I did here. We also dogfooded it, tracking our own work on the board while building it.

🎯 The Build
Boards contain columns, columns contain cards, with card position and column membership as first-class persisted data. Drag-and-drop is the centerpiece: a card moves the instant you release it, the board reflects the new order immediately, and the database catches up behind it via an async request. Task assignment sits on top, so ownership is visible at a glance.

Challenges

Drag-and-drop looks trivial from the outside — it isn't. Persisting order without rewriting the whole column on every move took several attempts to get stable. Cards have to move on drop before the server confirms anything, so I had to design deliberately for reverting a failed write without confusing the user. Concurrent edits from multiple people on the same board meant thinking carefully about how position updates are written and stale clients refresh. Building drag-and-drop in vanilla JS — pointer events, drop zones, placeholders, edge cases — was a long tail of small fixes. And the real challenge was leadership, not code: resisting the urge to write everything myself, letting three developers' approaches differ where it didn't matter, and defining structure before distributing work rather than after untangling merge conflicts.

Outcomes

DevBoard works and was genuinely used — by me and the three developers I led — to manage the very project it was built for. It proved the polished interactions people associate with heavy frontend frameworks are achievable without one, gave me a drag-and-drop implementation I understand at every level, and real technical leadership experience: owning architecture, dividing work, reviewing code, being accountable for the result. The biggest lesson wasn't the tool — it was that the architecture decisions you make in week one determine how much time everyone wastes in the months after.
